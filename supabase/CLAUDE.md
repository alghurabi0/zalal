# supabase/: SQL conventions

Loaded when Claude works in this folder. The root CLAUDE.md rules still apply. For a schema change, follow the `db-change` skill (`.claude/skills/db-change/SKILL.md`).

## Migrations
- Create with `pnpm exec supabase migration new <name>`. Never edit a migration that is on `origin/main` (the edit hook and the protected-paths CI check refuse it); add a new one.
- Start each file with a comment: what it adds, the spec sections it serves, and every departure from spec §7 with the reason. Update §7 in the same PR.
- Lowercase snake_case. Indexes `<table>_<columns>_idx`, unique indexes `<table>_<columns>_key`. Policy names are plain sentences ("Customers read their tanks; admins read all").
- Tables in `public`. Primary keys: `uuid` (`gen_random_uuid()`) for rows users own or that appear in URLs; `bigint generated always as identity` otherwise. Times are `timestamptz`, money is integer IQD, phones are E.164 checked with `^\+9647[3-9][0-9]{8}$`.
- Text columns get a length check and `= btrim(col)`; the app trims before sending.
- Every table with `updated_at` gets the `private.set_updated_at()` trigger.
- PostGIS lives in `extensions`: write `extensions.geography(point, 4326)`, `extensions.st_covers(…)`. Store `lat`/`lng` and generate the geography from them, so the app never handles PostGIS binary.
- `seed.sql` loads only locally (`db reset`, CI); hosted dev and prod never load it. A row any hosted project needs to work (the settings row, the starting service area, later prices and slots) goes in a migration that skips itself when the row already exists.
- Scheduled jobs: `cron.schedule` in the migration that owns the table. The schedule is UTC; comment the Baghdad time (UTC+3). Pick an off-hour minute, not :00.
- A job that calls an Edge Function goes through a `private` wrapper run by pg_cron (see `private.invoke_media_cleanup`). It reads `project_url` and the job's own secret from Vault (`vault.decrypted_secrets`), sends the secret in a custom header (the new secret keys aren't JWTs), and does nothing when either secret is missing, so the migration is safe before the owner adds them (`docs/supabase-setup.md` step 8). Never put a key or secret in SQL. A queued pg_net request (headers included) is readable by `anon` and `authenticated` through Supabase's default grants on `net.http_request_queue`, so never add `net` to the API's exposed schemas.

## Access: privileges, then RLS
- Supabase grants every privilege on new `public` tables and sequences to `anon` and `authenticated`, and EXECUTE on new `public` functions. So, for each table: `enable row level security`, `revoke all … from anon, authenticated` (and the same on its identity sequence), then grant only what each role needs. Use column grants to keep server-owned columns (`role`, `phone`, `deleted_at`, `last_cleaned_at`, …) out of reach. For each function, `revoke execute … from public, anon[, authenticated]` and grant it back to the roles that call it.
- Policies name their role (`to authenticated`, `to anon, authenticated`) and wrap calls so they run once per query: `(select auth.uid())`, `(select private.is_admin())`, `(select private.current_user_role()) = 'customer'`.
- Role helpers are in `private` (not exposed by the API): `private.current_user_role()` (null for guests and deleted accounts), `private.is_admin()` and `private.current_crew_id()` (the caller's crew while it is active and the account is still a crew; null otherwise).
- Postgres makes every new function executable by PUBLIC, and `alter default privileges in schema … revoke` can't undo that. End each migration that adds `private` functions with `revoke execute on all functions in schema private from public;`, then grant back only what policies call. `tests/database/rls_audit_private_execute.test.sql` fails if a migration forgets.
- Ownership across tables: when a child row carries `user_id`, reference the parent by `(id, user_id)` (see `tanks`), so a wrong policy still can't attach a row to someone else's parent.
- On UPDATE, Postgres also checks the new row against the SELECT policies. If a SELECT policy hides soft-deleted rows, a plain update can't soft-delete; do it in a `security definer` RPC (see `delete_address`).
- Certificates are issued only inside `transition_order` (`private.issue_certificate`); the server's service role sets `certificates.pdf_path`. Read a certificate as a guest only through `public_certificate(code)`, which returns nothing personal.
- Admin writes never go through table policies. They are `security definer` RPCs that check the role and call `private.log_admin_action(action, entity, entity_id, diff)` (`transition_order`, `assign_crew`, `admin_update_prices`, `admin_create_slot` / `admin_update_slot`, `admin_block_date` / `admin_unblock_date`, `admin_update_settings`, `admin_set_certificate_stamp`, `admin_save_service_area`, `admin_create_crew` / `admin_update_crew` / `admin_set_crew_phone`, `admin_add_admin` / `admin_remove_admin`, `admin_set_ticket_status`, `admin_add_ticket_note`, `admin_save_article` / `admin_delete_article`, `admin_save_category` / `admin_delete_category` / `admin_reorder_categories`, `admin_activate_subscription` / `admin_set_subscription_paid` / `admin_adjust_subscription_visits` / `admin_end_subscription` / `admin_add_subscription_note` / `admin_set_order_subscription`, and accounting's `admin_update_finance_settings`, `admin_save_finance_account`, `admin_save_expense_category` / `admin_delete_expense_category`, `admin_save_expense` / `admin_void_expense`, `admin_save_transfer` / `admin_void_transfer`, and revenue's `admin_save_payment` / `admin_void_payment`, `admin_save_discount` / `admin_void_discount`, `admin_save_manual_sale` / `admin_void_manual_sale`, and month close's `admin_close_finance_month` / `admin_reopen_finance_month`, and payroll's `admin_save_worker`, `admin_save_worker_crew` / `admin_move_worker` / `admin_delete_worker_crew`, `admin_save_worker_rate` / `admin_void_worker_rate`, `admin_save_payroll_adjustment` / `admin_void_payroll_adjustment`, `admin_set_worker_days`, and partners' `admin_save_partner`, `admin_set_partner_shares`, `admin_save_partner_movement` / `admin_void_partner_movement`, `admin_save_opening_equipment` / `admin_void_opening_equipment`, `admin_save_equipment_disposal` / `admin_void_equipment_disposal`, and stock's `admin_save_stock_item` / `admin_delete_stock_item`, `admin_save_stock_move` / `admin_void_stock_move`). Log only what changed, with old and new values; a save that changes nothing logs nothing. `private.audit_changes(old, new)` (migration `finance_ledger`) builds that diff from two jsonb objects. Admin-only reads that need a clear refusal (`admin_slot_board`, `admin_schedule_conflicts`, `admin_service_areas`, `admin_rating_summary`, `admin_customers`, `admin_revenue_summary`, `admin_expense_summary`, `admin_profit_and_loss`, `admin_expenses_by_category`, `admin_payroll`, `admin_worker_crew_days`, `admin_equipment`, `admin_partner_balances`, `admin_balance_sheet`, `admin_stock_items`, `admin_stock_month`) are `security invoker` with an explicit `private.is_admin()` check that raises `42501`.
- `orders.status` changes only through `transition_order()` (spec §6). No role has INSERT, UPDATE or DELETE on any order table; `create_order()` and `transition_order()` are the only writers. Child tables (`order_items`, `order_events`, `order_media`) read through `exists (select 1 from public.orders …)`, so the orders policy decides.
- Slot places: take one only with `private.reserve_seat(order_id, date, slot_id)` and free it with `private.release_seat(order_id)`. It queues on a transaction-level advisory lock per slot and day, checks the current capacity, then inserts the lowest free seat; the `slot_bookings` key stays as the backstop. Check a day and slot with `private.bookable_slot(date, slot_id, customer_rules)`.
- A storage policy that asks "is this file attached?" through a table the caller reads under RLS can be fooled by a caller who lost access to that table (an admin turned customer): check it without RLS through a `security definer` helper granted to `authenticated`, as `private.chat_media_sent` does for chat-media (RLS audit of migration `chat`), `private.ticket_media_attached` for ticket-media, `private.article_cover_used` for article covers and `private.certificate_stamp_used` for the certificate stamp in public-content. They are the only private functions besides the role helpers that `authenticated` may run (`rls_audit_private_execute.test.sql`).
- An RPC that attaches an upload must lock the file while it does (`update storage.objects … returning metadata`, not a plain select), and the "attached" helper must be `volatile`: otherwise the uploader can delete the file in the same moment, both commit, and the row points at a missing file. The upload policy also refuses the name of an attached file, so nothing else can take its place (RLS audit of migration `tickets_app`; `create_ticket`, `admin_save_article`, `admin_set_certificate_stamp` and, since migration `qa_retention`, `send_chat_message` do this). It also checks the file is the caller's own (`owner_id`) and finished (Storage's `metadata`).
- Articles (migration `articles`): `articles` and `article_categories` are written only by the A11 RPCs. A file the server deletes after an RPC frees it (a replaced or deleted article's cover) goes through the admin's own Storage client, never the secret key, so the delete policy still refuses a cover another article took meanwhile (RLS audit).
- Tickets (migration `tickets_app`): written only by `rate_order` and `create_ticket`; status changes only by `admin_set_ticket_status`, notes (`ticket_notes`, admins only) only by `admin_add_ticket_note`; files (`ticket_media`) only by `create_ticket`.
- Subscriptions (migration `subscriptions`): one per address. `subscriptions` is written only by `request_subscription` and the A7 RPCs, `subscription_notes` (admins only) only by them, and `orders.subscription_id` only by `create_order` and `admin_set_order_subscription`. Visits aren't stored: used = completed orders + `visits_adjustment`, held = open orders (`private.subscription_visits`). Anything that puts an order into a status that holds or uses a visit goes through `private.usable_subscription`, which locks the subscription row and raises `ZL034` (`create_order`, confirming, an override out of cancelled or no-show, A2's "استخدم الاشتراك"). Screens read `subscription_overview` (security invoker). A new `notification_type` value goes in its own migration before the one that uses it (Postgres can't use an enum value in the transaction that adds it).
- Accounts (migration `account_deletion`): `delete_account()` anonymizes a customer in one transaction (spec §7 "Accounts"). A new table holding a customer's personal data must be handled there (deleted or anonymized), and if a customer RPC inserts into it, it gets a `private.refuse_deleted_owner('<owner column>')` insert trigger, so a write racing the deletion is refused. A staff copy of that data must be handled too (admins' `customer_message` notifications keep an excerpt; migration `qa_retention`). The deletion also blanks `note`/`reason` in the account's `admin_audit_log` rows (`private.scrub_audit_text`), so a new audited admin RPC about a customer's row keeps its free text under one of those keys. `profiles.phone` is null only for a deleted account. A phone changes only through `change_login_phone` (service role, after the server's two codes), never the Auth admin API.
- Retention (migration `qa_retention`): `private.purge_expired_media()` (pg_cron `media-retention`) deletes booking-video rows 90 days after the order closed, and the `media-cleanup` customer folder then deletes the files; `unattached_media('certificate')` lists certificate PDFs nothing records (upload and last write over 24 h old). A new retention rule deletes rows and lets the cleanup delete the files, rather than deleting from Storage in SQL.
- Notifications (migration `notifications`): rows are written only by triggers and jobs, through `private.notify_user` / `notify_admins` / `notify_crew` (which skip deleted accounts and switched-off crews), and each insert statement queues its push (`private.queue_push` → `send-push`). A new event is a new `notification_type` value, its audience in the generated `notifications.audience` column (admin and crew types listed there; anything else is a customer's), an entry in ar.json `Notifications.items`, and a case in `describeNotification` and `notificationHref` (`src/lib/notifications/describe.ts`). Store the values the words need in `data`, never Arabic and never a staff note. Users read their rows only while they hold the row's audience role.
- Chat (migration `chat`): messages are written only by `send_chat_message` and the system triggers (`order_events` → no-show message, `tickets` → ticket message), read marks only by `mark_chat_read`. A new system message is a new `chat_message_kind` value plus its words in ar.json (`Chat.system`), never stored Arabic. Admin chat replies are not copied to `admin_audit_log` (the message names its sender and can't change).
- Accounting (migration `finance_ledger`, spec §8.3): admins read every finance table and `finance_account_balances` (security invoker); nobody else reads any, a crew not even its own box. Written only by the accounting RPCs. Money records are never deleted: void them (`voided_at`, `voided_by`, `void_reason`, all or none), and leave voided rows out of every total. A record's day goes through `private.finance_check_day`, which share-locks the `finance_settings` row so the start day can't move past it meanwhile; a box or category goes through `private.finance_check_account` / `finance_check_category`, which share-lock it so a switch-off at the same moment wins (RLS audit; `tests/integration/finance-ledger.test.ts`). A new crew gets its box from the `crews_create_finance_account` trigger.
- Revenue (migration `finance_revenue`): `finance_payments` (one item each: an order, a subscription or a manual sale; negative = a refund), `finance_discounts` and `manual_sales`, written only by their admin RPCs and, for the crew's cash, by the `order_events_record_crew_cash` trigger (`private.record_crew_cash`: once per order through the partial unique index on `automatic`, which counts voided rows; never blocked by a switched-off box). A payment or discount locks its item with `private.lock_finance_item` (after the settings share lock, so a start-day move can't deadlock with it) and checks the item's live payments with `private.finance_check_refunds`. What is in the books is `finance_receivables` (security invoker, filtered to admins: `orders` is readable by its customer); reports read it or `finance_customer_balances`, never recompute it. A subscription's `paid` is set only by `private.sync_subscription_paid` once it is in the books; call it after any payment or discount change on one. Anything that brings orders into the books (an earlier start day) runs `record_crew_cash` and `sync_subscription_paid` for them. `delete_account` (through `private.scrub_audit_text`) blanks the notes of the customer's payments, their discount reasons, sets their void reasons to `-deleted-` and scrubs their audit rows; a new free-text column about a customer's money goes there too.
- Month close (migration `finance_reports`): `finance_settings.closed_through` (null, or a month's last day) is set only by `admin_close_finance_month` / `admin_reopen_finance_month`, in order. Nothing dated on or before it changes: the `*_refuse_closed` triggers (`private.finance_refuse_closed`, the day column as its argument) on `expenses`, `finance_transfers`, `finance_payments`, `manual_sales` and `finance_discounts` check the old and new day of every insert and update, so a new finance table with a day gets one too, and a new writer needs no check of its own. A discount's day is its item's revenue day (`private.finance_item_revenue_on`). The only change let through is a non-admin's text-only update (account deletion's scrub of `note`, `reason`, `void_reason`). `private.finance_month_closed(day)` share-locks the settings row except for days in tomorrow's month (which can't close meanwhile), so a close and a save queue behind each other (`tests/integration/finance-month-close.test.ts`). `orders_guard_closed_month` refuses an override out of completed for an order completed in a closed month, and a completion landing in a month that closed at midnight (for orders completed on or after the start day; covered ones too since migration `finance_payroll`, as they are visits for per-visit pay); `subscriptions_guard_closed_month` does the same for an activation. `orders.completed_on` is kept by `order_events_set_completed_on` and that trigger; read it rather than looking up `order_events` (only `private.issue_certificate`'s backfill still does). Reports read `admin_profit_and_loss` / `admin_expenses_by_category`, which read `finance_receivables`.
- Payroll (migration `finance_payroll`): `workers`, `worker_crews`, `worker_rates`, `payroll_adjustments` and `worker_days`, admins only, written only by the payroll RPCs; `expenses.worker_id` only by `admin_save_expense`, on a `wages` category. Earned pay is never stored: `admin_payroll` computes it from the rates (each live rate runs until the next), the crew's completed orders (`orders.completed_on`), the ticked days and the adjustments, and the balance from the opening balance and the linked wages; screens read it, never recompute it. A new dated payroll table gets a `*_refuse_closed` trigger (`finance_refuse_closed` also checks a delete since this migration); `worker_crews` has its own (`worker_crews_refuse_closed`), which checks the earliest day a change touches, since closed months come before open ones. Every payroll writer share-locks the `finance_settings` row first, then the worker (`FOR UPDATE` for memberships and days, else a share lock through `private.payroll_check_worker`), then its record: a membership locked before its worker deadlocks with `admin_move_worker` (RLS audit), and the worker locked before the settings deadlocks with a queued month close (code review). A wage may pay a switched-off worker (`payroll_check_worker(id, false)`). `orders_guard_closed_month` now holds every order in the books (covered ones are visits). Anything that changes a worker's opening balance checks `closed_through` (`ZL056`).
- Partners and the balance sheet (migration `finance_partners`): `partners`, `partner_shares`, `partner_movements`, `opening_equipment` and `equipment_disposals`, admins only, written only by their RPCs; `expenses.useful_life_months` only by `admin_save_expense`. Shares are saved as a whole month's set (`admin_set_partner_shares`, which normalizes each partner id and refuses one named twice; RLS audit). Depreciation, profit shares and the balance sheet are computed, never stored: screens read `finance_equipment` / `finance_depreciation`, `admin_equipment`, `admin_partner_balances` and `admin_balance_sheet`. The profit (`admin_profit_and_loss`) accrues wages from `admin_payroll`, leaves out spread purchases and wages linked to a worker, adds the month's depreciation and the disposals' result; the cash columns still count every expense. `admin_balance_sheet` works out each side from its own records and returns `balanced`: a new money record must reach both sides (a box through `finance_account_balances` and the balance sheet's own box sum, and the profit or an equity line), or it breaks. Anything that changes an opening balance (boxes, workers, partners, opening equipment) checks `closed_through` (`ZL056`), since the balance sheet shows past months. The new dated tables have `*_refuse_closed` triggers; writers share-lock the settings row first, then the partner, purchase or opening item, then the record.
- Stock (migration `finance_stock`): `stock_items` and `stock_moves` (in, out, count), admins only, written only by their RPCs. Quantities only, numeric(12,2): stock has no value, so nothing here reaches `admin_profit_and_loss` or `admin_balance_sheet`; if stock ever carries a value, it must reach both sides of the balance sheet. Quantities on hand are computed, never stored: screens read `admin_stock_items` / `admin_stock_month`, which read the view `stock_levels` (a count is the quantity at the end of its day; `recorded` is what the records alone made it). After any change `private.stock_after_change` (the item locked) refuses a quantity below zero at a day's end or before a count (`ZL065`) or above 1,000,000,000, and sends `stock_low` to admins when a switched-on item drops to its minimum. Writers lock the settings row (share), then the item (`FOR UPDATE`, so the quantity check sees every record), then the record, then a linked expense and its category (`FOR SHARE OF e, c`: a void of the expense or a move of its category off general waits and then sees the record; RLS audit). The triggers `expenses_guard_stock` and `expense_categories_guard_stock` keep a linked expense live, dated on or before its ins and in a general category (`ZL064`), so `admin_save_expense`, `admin_void_expense` and `admin_save_expense_category` needed no change. `stock_moves_refuse_closed` covers month close; `admin_update_finance_settings` counts stock records for `ZL046`.
- Storage policies go in the migration of the tables that own the files, scoped by `bucket_id`, and in `storage_buckets.test.sql`'s `policies_are` list. Direct SQL deletes from `storage.objects` are refused unless `storage.allow_delete_query` is on (the Storage API sets it); tests set it to check the delete policy.

## Functions
- RPCs the app calls go in `public`; trigger functions and helpers go in `private`.
- Prefer `security invoker`. Use `security definer` only when the caller must not have the table privilege. Then: `set search_path = ''` (the guards check it), fully qualified names everywhere, and an explicit `auth.uid()` check inside.
- Server-only RPCs (OTP limits, `unattached_media`) grant EXECUTE to `service_role` only. The app or an Edge Function calls them with the secret key.
- `auth.users` has a guard trigger (`private.guard_auth_user`, migration `auth_user_guard`): no new email (a row that already has one keeps it), and a password changes only inside `public.set_login_password(user_id, password)` (service role), which marks its own transaction with the setting `zalal.password_set_for`. Never set a password through the Auth admin API (the trigger refuses it); call that RPC. Tests that insert into `auth.users` must not set `email`.
- Auth hooks are Postgres functions in `private`, granted EXECUTE to `supabase_auth_admin` only (which has USAGE on `private` for that). The Send SMS Hook `private.refuse_auth_sms` refuses every send: phone codes are made and checked by the server (spec §9.1), and users are created through the Auth admin API, since sign-ups are off. Staff accounts too: the server makes the account (`ensureAccount` in `src/lib/admin/staff-accounts.ts`), then the admin RPC decides whether it may be a crew or an admin (`private.is_untouched_account`, `private.lock_account`).
- Errors the app shows: `raise exception using errcode = …, message = '<snake_case_code>'`. The app maps the code to an `ar.json` string. Codes in use:
  - `ZL001` `outside_service_area`
  - `ZL002` `password_change_not_allowed` and `ZL003` `email_not_allowed` (the `auth.users` guard; Auth's API reports them as a failed update, the app never shows them)
  - `ZL004` `slot_unavailable` (inactive, wrong weekday, blocked, in the past, or inside the cutoff; no booking window since migration `no_booking_limits`), `ZL005` `slot_full`, `ZL006` `change_too_late` (customer cancel, reschedule or postpone once the slot has started; until migration `postponed_orders`, inside the cutoff), `ZL007` `too_many_tanks` (retired by migration `no_booking_limits`: no tank limit), `ZL008` `too_many_files` (booking, the crew's 10 / 10 / 4 per order, and the Issue report's 3), `ZL009` `upload_not_found` (missing, unfinished, someone else's, outside the folder, already attached, or, for `create_order`, uploaded more than 48 h ago)
  - `ZL010` `invalid_transition`; `ZL011` a missing requirement: `cash_not_collected`, `crew_not_assigned`, `reason_required`, `sterilant_required` (crew completion, C4) (`before_photo_required` and `after_photo_required` were retired by migration `crew_jobs`: photos are optional)
  - `ZL012` `address_in_use` (`delete_address` while an active order uses it)
  - `ZL013` `crew_inactive` (assigning a switched-off crew, or one whose account is no longer a crew), `ZL014` `crew_change_not_allowed` (changing the crew after the crew arrived, or removing it while on the way)
  - `ZL015` `slot_exists` (a new slot with the times of another, switched off or not), `ZL016` `invalid_area` (a service area that isn't a valid polygon inside Iraq, or has more than 5,000 points), `ZL017` `last_active_area` (switching off the only active area), `ZL018` `price_changed` (`create_order`'s `expected_total` no longer matches the prices)
  - `ZL019` `phone_has_account` (a crew needs an untouched account: a customer that never signed in and owns nothing), `ZL020` `crew_name_taken`, `ZL021` `account_is_crew` (a crew account can't become an admin), `ZL022` `cannot_remove_self`
  - `ZL023` `media_not_allowed` (`attach_job_media` / `remove_job_media` on a job that isn't arrived or in progress; attach also takes 24 h after completion)
  - `ZL024` `location_not_allowed` (`share_crew_location` on a job that isn't on the way)
  - `ZL025` `rating_not_allowed` (`rate_order` on an order that isn't completed), `ZL026` `already_rated`
  - `ZL027` `too_many_messages` (`send_chat_message`: 20 a minute per sender)
  - `ZL028` `ticket_order_too_old` (`create_ticket` on an order whose slot was more than 90 days ago), `ZL029` `too_many_tickets` (`create_ticket`: 5 app tickets an hour per customer)
  - `ZL030` `category_in_use` (`admin_delete_category` while an article uses it), `ZL031` `slug_taken`, `ZL032` `slug_locked` (`admin_save_article`: a new slug for an article that has been published), `ZL033` `category_name_taken`; `ZL009` also covers a cover that isn't the admin's own recent upload in `public-content/articles/` or is used by another article, and a certificate stamp that isn't the admin's own upload in `public-content/stamp/` under 48 h old
  - `ZL034` `subscription_unavailable` (`create_order`, confirming or reviving a covered order, A2: the message is the reason, `no_subscription`, `outside_subscription_period`, `no_visits_left`, `subscription_tanks_exceeded`), `ZL035` `subscription_exists` (a request, or an activation, while the address has a subscription running more than 30 days or overlapping), `ZL036` `invalid_subscription_status` (an A7 action for another state), `ZL037` `subscription_not_offered` (no plan price), `ZL038` `subscription_change_not_allowed` (`admin_set_order_subscription` on a completed order, or putting coverage on one not waiting for its visit); `ZL011` `reason_required` also covers A7's adjust, decline and cancel; `ZL012` also covers an address with a live subscription

## Edge Functions (`functions/<name>/`)
- `index.ts` only reads `Deno.env` and calls `Deno.serve`; it is left out of `tsc` (`tsconfig.json`). Code shared by functions goes in `functions/_shared/` (`edge.ts`: `serviceKeyFrom`, `sameSecret`, `json`), which the deploy skips; import it with the `.ts` extension, as Deno needs (`allowImportingTsExtensions` is on). Everything else goes in a plain module (see `media-cleanup/cleanup.ts`) with no Deno APIs, which `tsc`, ESLint and Vitest check: unit tests with a fake client in `tests/unit/`, and the real database and Storage in `tests/integration/`. `deno.json` maps `@supabase/supabase-js` and `zod` to the exact versions in `package.json`.
- Called by pg_cron, not users: `verify_jwt = false` in `config.toml` and a check of the job's own secret, compared in constant time. The service key is `SUPABASE_SECRET_KEYS` (`default`), falling back to `SUPABASE_SERVICE_ROLE_KEY`; `serviceKeyFrom` reads it. Validate the body with Zod, log counts only (paths carry user ids), and keep the rules in SQL so pgTAP tests them.
- CI deploys every function (`.github/actions/supabase-deploy`) but doesn't run the edge runtime, which `db:start` leaves out. To try one by hand: `supabase functions serve <name> --env-file <file>` (it pulls the edge-runtime image), or run `index.ts` with a Deno 2 binary, `--config` set to its `deno.json`.

## pgTAP tests (`tests/database/`)
- One file per table or RPC, `<name>.test.sql`, opening with a comment that states the rules. Start with `begin;` and `\ir _helpers.psql`, end with `select * from finish(); rollback;`.
- Helpers: `tests.create_user(phone[, role])`, `tests.user_id(phone)` (usable inside `$$…$$`), `tests.authenticate_as(id)`, `tests.authenticate_as_anon()`, `tests.authenticate_as_service_role()`, `tests.clear_authentication()`.
- Booking fixtures (insert as the test runner, before authenticating): `tests.create_address(user_id[, label])`, `tests.create_crew(phone)` (a crew account and its `crews` row), `tests.create_slot(start, end[, capacity])` (every weekday), `tests.create_order(customer_id[, status, slot_start_at, crew_id, slot_id])` (holds a place unless cancelled or postponed; `slot_start_at` is stored as given, so a test can place it anywhere relative to `now()`), `tests.create_object(bucket, name, owner[, mimetype, size])` (a finished upload), `tests.create_subscription(user_id[, status, starts_on, visits, tanks, address_id])` (requested, or active for 12 months from `starts_on`, on the user's default address unless given; Phase 6). Keep ids by name with `insert into tests.ids` and `tests.id(name)`.
- Realtime: a table in the `supabase_realtime` publication sends INSERT and UPDATE events through RLS, but DELETE events go to every subscriber with the primary key. Give such tables a key that says nothing (not an order or user id), and have screens subscribe to INSERT/UPDATE only (`usePostgresChanges` in `src/lib/supabase/`). Changes made before a subscription is live aren't sent: a screen that must not miss one reads again in `onSubscribed` (Chat, the tab dot, the inbox). `rls_audit_live_job.test.sql` runs events through `realtime.apply_rls()`.
- Concurrency (two bookings at once) can't be tested in one pgTAP transaction; it lives in `tests/integration/booking-capacity.test.ts`.
- Cover allowed and denied for anon, customer, another customer, crew and admin on every policy, plus the service role where the server writes.
- Expected errors: `42501` permission or RLS `with check`, `23514` check, `23505` unique, `23503` foreign key, `23502` not null. A row hidden by RLS doesn't error; test it with `is_empty($$ update … returning 1 $$)`.
- `now()` is fixed inside the test's transaction: backdate rows to test time windows. To backdate `updated_at`, disable its trigger around the update.
- Don't depend on seed data: replace it in the test (for example `delete from public.service_areas` and insert a test area).
- Write the tests first and watch them fail. Fix the `plan(n)` count last.
