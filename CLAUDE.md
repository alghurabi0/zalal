# Zalal — rules for Claude Code

Arabic (Iraqi dialect), RTL, mobile-first PWA for booking water-tank cleaning in Karbala. One Next.js 16 (App Router) app, three surfaces: customer `/`, crew `/crew`, admin `/admin`. Backend: Supabase (Postgres + RLS + RPC, Auth, Storage, Realtime). Deployed on Vercel.

## Sources of truth
- Spec: docs/spec.md. Read the sections your task needs; section numbers are stable (§5 screens, §6 order lifecycle, §7 data model, §12 phases).
- Designs: design/*.dc.html. These are read-only, so never edit them. Read the screen's design file before building it, and match layout, copy and tokens exactly unless the spec lists a change. Where the spec and a design disagree, the spec wins.
- The design files are canvas exports. `{{…}}` are template slots filled by the inline script, and `[brackets]` are sample data that comes from the database. They load a `support.js` that is not in the repo, so read them as source code; they won't render on their own. For how a screen looks, use `design/png/<Name>.png`, the exported image of the same artboard (2×, 780×1688). The PNGs show only the first screen (844px tall); for content below the fold, the `.dc.html` is the source.
- The spec §7 schema is a starting point, not a contract. Design the real schema yourself and improve it where you can, as long as the behavior and rules in the spec still hold. Explain each departure in the migration and the PR, and update §7 to match.
- If the spec is unclear or contradicts itself on a business rule, ask. Don't guess. Add unresolved questions to spec §13.
- Out-of-scope items (spec §1) stay out, even when they would be easy to add.

## Commands
Keep this list in sync with package.json.
- `pnpm dev`: run the app (no service worker); `pnpm build` / `pnpm start`: production build. `pnpm build` runs `next build && serwist build`, which writes the service worker `public/sw.js` from `src/app/sw.ts` (spec §3, "PWA and caching").
- `pnpm icons`: regenerate the PWA icons and favicons from `public/brand/logo.svg`, then commit them
- `pnpm lint` (ESLint, then the guards) / `pnpm typecheck` (`next typegen` + `tsc`) / `pnpm test` (Vitest, `tests/unit/`; component tests are `.test.tsx` with `// @vitest-environment happy-dom` and render via `react-dom/server`)
- `pnpm test:integration`: Vitest against the running local Supabase (`tests/integration/`, `vitest.integration.config.ts`): real SQL functions, Auth and its admin API, for example the whole OTP login
- `pnpm guards [files]`: `scripts/guards.ts`, the rules below that ESLint can't check: no left/right classes or properties, no raw colors (hex, `rgb(`, `oklch(`…) outside the theme, illustrations and `src/lib/brand.ts`, no arbitrary Tailwind values, no Arabic in `src/**/*.ts(x)`, `enable row level security` for every table in the migration that creates it, and `set search_path = ''` on every `security definer` function. For a justified exception, comment `guard-allow <rule>: <reason>` on the line or the line above.
- `node scripts/protected-paths.ts [base]`: fails if the branch changed or deleted files in `design/` or `supabase/migrations/` since `base` (default `origin/main`)
- `pnpm format` / `pnpm format:check`: Prettier, which also sorts Tailwind classes
- `pnpm test:e2e`: Playwright at a 390×844 viewport (`tests/e2e/`; admin tests use 1280×800 with `test.use`, since admin is desktop-first); builds and starts the app on port 3100 against the running local Supabase. The server gets `OTP_DEV_OUTBOX`, so login codes are also written to `test-results/otp-outbox/<phone>`; log in through the UI with `tests/e2e/helpers/auth.ts` (`signUp`, `requestCode`, `enterCode`, `skipSendLimits`), and set up data screens can't (roles, settings) with `tests/e2e/helpers/supabase.ts`. Booking tests make their own slot with `createSlot()` (`tests/e2e/helpers/booking.ts`, also `fillSlot`, `baghdadDate`, `pickSlot`, and `createOrder` for an order in any status or near the cutoff), so parallel runs never take each other's places; admin tests log in with `logInAsAdmin()` and make customers and crews with `createCustomer()` and `createCrew()`, and crew tests log in with `logInAsCrew()` (`tests/e2e/helpers/admin.ts`; `createOrder({ crewId })` assigns the job, `createOrder({ subscriptionId })` covers it; `createCertificate(orderId)` issues a completed order's certificate; `createSubscription(phone, { status, visits, tanks })` adds a request or an active subscription on the customer's first address); Tips tests make their own categories and articles with `createCategory()` and `createArticle()` (`tests/e2e/helpers/articles.ts`) and never feature one, since featured articles change Tips' top card and Home's strip for every test; `stubPush(page, endpoint)` (`tests/e2e/helpers/push.ts`) fakes the push permission and subscription; media fixtures are in `tests/e2e/fixtures/`. Order fixtures write notifications through the database triggers; clear a user's rows first when a test counts them. The server also gets `CERTIFICATE_CHROMIUM_PATH` (Playwright's Chromium), so it can make certificate PDFs. Use a fresh `newPhone()` per test. In cloud sessions, set `PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium`, because the pre-installed Chromium doesn't match the pinned Playwright version. Don't run `playwright install` there.
- `pnpm db:start` / `pnpm db:stop`: local Supabase in Docker, without the services tests don't need (Studio, image proxy, logs, pooler, Edge runtime, postgres-meta)
- `pnpm db:reset`: `supabase db reset` (migrations + `supabase/seed.sql`)
- `pnpm db:test`: `supabase test db` (pgTAP in `supabase/tests/database/*.test.sql`). Each test starts with `begin;` and `\ir _helpers.psql`, which adds `tests.create_user(phone[, role])`, `tests.user_id(phone)`, `tests.authenticate_as(id)`, `tests.authenticate_as_anon()`, `tests.authenticate_as_service_role()` and `tests.clear_authentication()` inside the test's transaction, plus booking fixtures (`tests.create_order`, `create_slot`, `create_crew`, `create_address`, `create_object`, `create_subscription`; listed in `supabase/CLAUDE.md`).
- Edge Functions: `supabase/functions/<name>/`, deployed by CI with the migrations (`media-cleanup`, `send-push`; shared helpers in `_shared/`, which isn't deployed). The logic is a plain module that Vitest tests; `index.ts` is Deno only (conventions in `supabase/CLAUDE.md`).
- `pnpm db:types`: regenerate `src/lib/database.types.ts` from the local database (then Prettier). Never edit that file by hand.
- `node scripts/write-env-local.mjs`: write `.env.local` from the running local Supabase (keeps an existing file unless `--force`)
- CI (`.github/workflows/ci.yml`) runs on every PR: `format:check`, `lint`, `typecheck`, `test`, then `db:start`, `db:test`, `test:integration`, a check that `database.types.ts` matches the schema, and `test:e2e`. `.github/workflows/protected-paths.yml` runs `protected-paths.ts`; the owner's `protected-change` label skips it for a deliberate design update (never add it yourself). All three jobs must pass to merge.
- Claude Code config (`.claude/`, docs/claude-code-setup.md §3): `settings.json` allows the commands above without prompting and denies reading `.env` files, editing `design/`, and Supabase commands against a hosted project. Its hooks refuse edits to `design/`, `database.types.ts` and merged migrations, and run Prettier, `eslint --fix` and the guards after each edit; fix what they report. Skills: `/build-screen <Name>`, `/ship-task`, and `db-change` for any SQL change. Subagent: `rls-auditor` (`.claude/agents/`), run after adding or changing tables, policies, grants or RPCs. SQL conventions: `supabase/CLAUDE.md`.

## Environments
- You work against **local Supabase only** (Docker). In cloud sessions the SessionStart hook (`.claude/hooks/session-start.sh`) installs packages, starts Docker, and starts Supabase in the background (log: `/tmp/supabase-start.log`; the first image pull takes a few minutes). It also writes `.env.local` from the local keys and sets `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io`, which the CLI needs there because the default registry is blocked.
- App code reaches Supabase only through `src/lib/supabase/`: `browser.ts` (client components), `server.ts` (Server Components, Actions, route handlers; acts as the user) and `admin.ts` (secret key, bypasses RLS, server only). Env vars are validated in `src/lib/env.ts` and `src/lib/env.server.ts`; `.env.example` lists them.
- Login codes: without `OTPIQ_API_KEY` (the normal state locally and in CI), `requestOtp` prints each code in the `pnpm dev` terminal instead of sending it. Don't add an OTPIQ key to `.env.local`. `OTP_DEV_OUTBOX` (e2e only, refused on Vercel and with a key) also writes each code to a file.
- Certificate PDFs (spec §10.1) need a Chromium: Vercel uses `@sparticuz/chromium`; elsewhere set `CERTIFICATE_CHROMIUM_PATH` (in cloud sessions `/opt/pw-browsers/chromium` for `pnpm dev`; the e2e server gets it from Playwright). Without it the download shows an error, which is fine for work that doesn't touch PDFs.
- Google Maps: `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` is unset locally and in CI, and Location then shows a drawn map (spec §5.4). Don't add a key to `.env.local`; test the keyless path.
- Web Push (spec §9.2): `NEXT_PUBLIC_VAPID_PUBLIC_KEY` is unset locally and in CI, so the app never offers push, and the `send-push` trigger sends nothing without its Vault secrets. Don't add VAPID keys to `.env.local`. The e2e server gets a test public key (`tests/e2e/helpers/push.ts`), and tests stub the browser's subscribe with `stubPush()`; unit and integration tests make throwaway key pairs with `web-push`. The service worker exists only in `pnpm build`, so push can't be tried under `pnpm dev`.
- Dev and prod are hosted projects that CI deploys to (docs/supabase-setup.md). Never run `supabase link`, `db push` or `functions deploy` against a hosted project yourself, and never ask for or handle hosted keys.
- Releases (docs/deploy-setup.md): PRs get a Vercel preview on dev Supabase; merges to `main` migrate dev; the owner runs the approved "Deploy prod" workflow, which migrates prod and then deploys the app. Vercel never deploys `main` by itself (`vercel.json`), so a migration must work with the app code merged alongside it.
- Sentry and PostHog are off without `NEXT_PUBLIC_SENTRY_DSN` / `NEXT_PUBLIC_POSTHOG_KEY`, which is the normal state locally and in CI. Don't add their keys to `.env.local`.

## Next.js 16 notes
- Check the current Next.js docs before using an API you're unsure of. Version 16 changed things, for example `proxy.ts` replaces `middleware.ts`, and `params`, `searchParams`, `cookies()` and `headers()` are async. The docs for the installed version are in `node_modules/next/dist/docs/` (see AGENTS.md, which `next dev` keeps in the repo).
- `cacheComponents` and `partialPrefetching` are on (the Next 16.4 defaults). Uncached request data (`cookies()`, `headers()`, `searchParams`) must sit under a `<Suspense>` boundary; see `node_modules/next/dist/docs/01-app/02-guides/migrating-to-cache-components.md`.
- Default to Server Components. Add `"use client"` only for interactivity, and keep client components small.
- Code that reads the clock in a page (the Supabase auth client does) must run at request time: `createClient()` in `src/lib/supabase/server.ts` calls `connection()` first, so use it rather than a client of your own.
- Next keeps recently visited pages alive (hidden, with their state). A form that must start fresh gets a `key` from its data (see Location and OTP), and a sheet closes before a link inside it navigates away. In e2e tests, hidden copies of a page can match a locator; use `.filter({ visible: true })`.
- Sessions and routing: `src/proxy.ts` refreshes the session and sends guests on login-only pages (`loginRequiredPrefixes` in `src/lib/routes.ts`) to Login with `?next=`. Add new login-only routes there, and still check on the server with `requireViewer()` (`src/lib/auth/viewer.ts`). Read `next` only through `safeNext()`.

## UI rules
- RTL only. Use logical CSS (ms-/me-/ps-/pe-/start-/end-/text-start, rounded-s/e), never left/right (ml-, pr-, left-, text-left, rounded-l…). Flip directional icons such as arrows and chevrons.
- Wrap phone numbers, times, codes and order numbers in `dir="ltr"`. Use Western digits (0–9), as in the designs.
- All UI strings go in messages/ar.json, grouped by screen (Iraqi Arabic, copied from the designs). No Arabic literals in components. Read them with next-intl: `useTranslations("Screen")` in components, `getTranslations` in async server code. Keys are type-checked against ar.json. The locale is fixed to `ar` (no `/ar` prefix in URLs) and the time zone to Asia/Baghdad in `src/i18n/request.ts`.
- Colors, radii, sizes and shadows come from the Tailwind v4 `@theme` tokens only. No raw hex and no arbitrary values (`bg-[#…]`, `rounded-[13px]`) in components. If a design value has no token, add the token (spec §4 lists the known gaps). Tailwind's default colors, radii, font sizes, line heights, letter spacing and shadows are removed, so only design tokens exist. Radii use role names (`rounded-chip`, `rounded-input`, `rounded-button`, `rounded-card`, `rounded-t-sheet`), circles and pills use `rounded-full`, and font sizes are in px (`text-15`). Spacing uses Tailwind's 4px scale (`p-5.5` = 22px).
- Reuse src/components/ui before you create a component (spec §4 "UI kit" lists them; `/kit` shows them all). Join classes with `cn()` from `@/lib/cn` so a passed `className` overrides defaults. Icons come from lucide-react, matched to the canvas glyph, with `aria-hidden` on decorative ones.
- Kit strings live in the `UI` namespace of ar.json; demo text for `/kit` lives in `Kit`. Link to customer screens through `routes` in `src/lib/routes.ts`, not string literals.
- Pad bottom bars and sheets with `pb-safe-*` (clears the iPhone home indicator), not plain `pb-*`.
- Admin-written Markdown (articles, Terms, Privacy) renders only through `MarkdownText` (`src/components/articles/markdown.tsx`): React elements, raw HTML dropped, safe links only. Never `dangerouslySetInnerHTML`.
- Every screen has loading (skeleton), empty (with CTA), error ("اعد المحاولة") and offline ("ماكو انترنيت") states.
- Accessibility: touch targets of at least 44px, an Arabic aria-label on icon-only buttons, a visible focus state.

## Data and security rules
- TypeScript strict. No `any`, and no `@ts-ignore` without a comment explaining why.
- Zod validates every input at the boundary (Server Actions, route handlers, Edge Functions). Share schemas between client and server.
- Writes go through Server Actions or Postgres RPC. Never update orders.status directly; use transition_order().
- Phone login goes only through `src/lib/otp` (`requestOtp`, `verifyOtp`), which makes, sends and checks the code itself (spec §9.1). Never use Supabase Auth's phone OTP (`signInWithOtp`, `auth.verifyOtp`, `resend`, `updateUser({ phone })`): its Send SMS Hook refuses every send, by design.
- Enforce business rules (2 h cutoff, slot capacity, service area, OTP limits) in Postgres or on the server. A UI check alone is never enough.
- Every table has RLS enabled. Add a pgTAP test for every policy, covering both allowed and denied cases for anon, customer, other customer, crew and admin.
- Migrations: create them with `supabase migration new`. Never edit a migration once it is merged; add a new one instead. After any schema change, run `pnpm db:types` and commit the generated types.
- The Supabase service-role key is used only in server code (`import "server-only"`). Secrets live in `.env.local`, Vercel's server env (the OTPIQ key) or Supabase secrets, never in git or client code. Only `NEXT_PUBLIC_*` values may reach the browser.
- Money is integer IQD; format it with formatIQD(). Store dates as timestamptz; compute and display them in Asia/Baghdad via lib/dates. Never base a business rule on the device's time zone.
- Phones are stored as E.164 `+9647XXXXXXXXX`; normalize them via lib/phone.
- Never send personal data (phone, name, address, OTP, photos) to Sentry or PostHog: no `Sentry.setUser` with a phone, no PostHog properties holding them. Identify PostHog users by user id only and call `posthog.reset()` on logout. Every `error.tsx` calls `useReportError(error)` from `src/lib/monitoring/use-report-error.ts`.
- `/zl-e` (Sentry) and `/zl-a` (PostHog) are forwarding paths (`src/lib/monitoring/paths.ts`). Keep them out of `proxy.ts` matchers and service-worker caching.

## Workflow
- One task per branch and per session. For anything that touches schema, RLS, auth or more than a few files, plan first and wait for approval.
- Write the test first for RPCs and rules (transition_order guards, slot capacity, 2 h cutoff, RLS).
- Before you call a task done, run `pnpm lint && pnpm typecheck && pnpm test`, plus `pnpm db:test` if SQL changed. For UI work, screenshot the screen at 390×844 (Playwright) and compare it with `design/png/<Name>.png`.
- Commit each logical change with a clear message.
- Don't add libraries without saying why in the PR description. Use current stable versions, and check the library's current docs rather than memory (Next.js, Supabase, Tailwind v4 and Serwist change fast).
- Keep the docs true. If you change a decision, update docs/spec.md. If you add a command or convention, update this file.
